# C09 Resend Email and Deep Links Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver Better Auth verification and reset email through a durable Resend outbox and safe HTTPS landing pages.

**Architecture:** Better Auth callbacks enqueue minimal token-bearing payloads into the existing `email_task` table. A dedicated email worker claims leased tasks, sends through Resend with the stable delivery UUID as its idempotency key, removes successful/expired rows, and retries bounded transient failures. Fixed landing pages bridge HTTPS email links to the configured app scheme; the generic C16 worker stays separate.

**Tech Stack:** Node.js 24, TypeScript, Hono, Better Auth 1.7.7, PostgreSQL/Drizzle, Resend HTTP API, Vitest, Docker Compose.

## Self-review

- `NEW-AUTH-02` is covered by queued verification email, safe verified landing, and resend cooldown; Better Auth enforces the configured one-hour verification expiry.
- `NEW-AUTH-04` is covered by generic reset response, valid/expired/reused reset tokens, session revocation, safe reset landing, and the same email delivery path.
- Tokens remain in the existing minimal JSON outbox payload only while queued/in flight; successful and expired tasks are deleted. Retry preserves one stable Resend key for the task's lifetime.
- No schema change is planned because the existing table has kind, payload, expiry, status, attempts, next-attempt, lease token, lease expiry, and delivery UUID.
- Signup returns a generic 503 and rolls back account creation when verification enqueue fails; reset enqueue failures preserve the generic response and allow a later retry.
- Real domain verification and real inbox delivery remain environment acceptance, not claims made by local integration tests.
