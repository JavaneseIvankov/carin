# Real AI Demo Seed Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Do not replace live AI output with fixtures.

**Goal:** Add an explicit, repeatable Carin API command that fills a verified demo account with profile, examination, consumption, and six real-AI photo-analysis records.

**Architecture:** A Node CLI uses Better Auth sign-in and authenticated App API endpoints for product data. A small database registry stores seed keys and resource IDs so runs can resume without duplicates; photos still go through private media upload and durable worker jobs. The CLI fails closed unless the account is verified, AI consent is already granted, and every analysis result has `dataMode: real`.

**Tech Stack:** Node.js 24, TypeScript, pnpm, Hono App API, Better Auth, Drizzle/PostgreSQL, MinIO, existing AI worker/provider.

## Task 1: Add durable seed state

**Files:** `carin-api/src/db/schema/demo-seed.ts`, `carin-api/src/db/schema/index.ts`, generated `carin-api/drizzle/*`.

- [ ] Define a `demo_seed_resource` table with UUID primary key, `user_id` FK with cascade, stable `seed_key`, `resource_kind`, `payload_hash`, nullable `resource_id`, `state` (`pending` or `complete`), and server timestamps.
- [ ] Add a unique constraint on `(user_id, seed_key)` and an index on `(user_id, resource_kind)`. Give each operation a distinct key such as `profile:v1`, `photo:<filename>:<sha256>`, and `analysis:<filename>:<sha256>` so upload and analysis job IDs are tracked separately.
- [ ] Export the table from the schema index.
- [ ] From `carin-api/`, run `pnpm run db:generate`; inspect the generated SQL and snapshots, retaining the generated migration name and appending it after `0012_onboarding_completion`.
- [ ] Keep seed-registry rows separate from product records. Only rows belonging to the authenticated demo user may be read or changed.

## Task 2: Add the authenticated API client

**Files:** `carin-api/src/demo/api-client.ts`.

- [ ] Read `DEMO_API_URL`, `DEMO_EMAIL`, `DEMO_PASSWORD`, and `DEMO_SEED_TARGET_EMAIL` from the process environment. Require the target email and sign-in email to match exactly; reject missing values and non-HTTP(S) origins. Never print values or cookies.
- [ ] Sign in through `POST /api/auth/sign-in/email`; preserve response cookies with Node's `Headers.getSetCookie()` and send them on subsequent requests.
- [ ] Immediately call `GET /api/v1/me`; require matching `DEMO_EMAIL` and `emailVerified === true` before any mutation.
- [ ] Read `GET /api/v1/legal` and `GET /api/v1/profile`, `GET /api/v1/onboarding`; use the current AI consent version and reject if `me.aiConsent.granted` is false. Do not grant consent on behalf of the account.
- [ ] Implement typed JSON and multipart helpers that attach the session cookie, `Idempotency-Key`, and `Content-Type` correctly. For multipart requests let `fetch` set the boundary.
- [ ] Require `DATABASE_URL` for seed-state persistence. Derive stable UUID idempotency keys from `(userId, seedVersion, seedKey, operation)` using SHA-256, setting UUID version/variant bits deterministically.
- [ ] Reject non-2xx responses with method/path/status/error code only; never print response bodies containing profile, food, or auth data.

## Task 3: Define stable synthetic profile and history inputs

**Files:** `carin-api/src/demo/seed-data.ts`.

- [ ] Define one complete profile object with explicit knowledge states and synthetic values. Use only the contract enums: `sexForReference: female|male`, activity `sedentary|light|moderate|high`, smoking `never|former|current`; do not create reported diagnoses or clinical claims.
- [ ] Set profile knowledge explicitly, for example `diagnoses: { state: 'none_known', entries: [] }`, `familyHistory: { state: 'unknown', entries: [] }`, and `allergies: { state: 'unknown', entries: [] }`.
- [ ] Define valid examination points for pressure, fasting glucose, and cholesterol total/LDL/HDL. Store dates relative to the run date in `Asia/Jakarta`, with at least two points per charted series and no clinical interpretation.
- [ ] Define several valid manual meals on today and recent dates. Since catalog matching is not available for the demo photos, use `catalogVersion: 'unavailable'`, null scan/result IDs, occurrence `new_occurrence`, and explicit unknown portions where needed. Use current API schemas; do not invent nutrient totals.
- [ ] Enumerate the six sorted `.jpeg` files in `carin-api/fixtures/demo/`. Derive stable seed keys from filename plus SHA-256 so a changed file becomes a new item without silently replacing an old result.

## Task 4: Implement the seed registry and orchestration

**Files:** `carin-api/src/demo/seed-state.ts`, `carin-api/src/demo/seed.ts`.

- [ ] Implement reserve/read/complete operations for registry rows using `user_id` from authenticated `/me`; a pending reservation must retain its stable API idempotency key so a rerun can resume an operation.
- [ ] Reject if `APP_ENV` is missing or `AI_MODE` is explicitly `fixture`. Require the operator guide to set the worker container to `AI_MODE=real`; never change worker configuration in the seed command. Verify each returned result is real before retaining the scan.
- [ ] Apply profile through `PATCH /api/v1/profile` with `expectedVersion` from the current profile. If the registered profile payload hash already matches, skip it; otherwise update only the dedicated seed account using the current version.
- [ ] If onboarding is incomplete for the demo account, call `POST /api/v1/onboarding/complete` after profile persistence. Do not change routes or onboarding state for any other account.
- [ ] Create each examination and manual consumption through its normal endpoint using a stable idempotency key. Persist returned IDs before proceeding to the next resource.
- [ ] For each photo, reserve the asset key, upload with `POST /api/v1/photos`, create a job with `POST /api/v1/analysis-jobs`, and poll `GET /api/v1/analysis-jobs/{id}` with bounded exponential backoff and `Retry-After` support.
- [ ] Stop on terminal job failure. On completion, require a result with `dataMode === 'real'`, preserve the returned result and its limitations, and reject any result containing `kind: synthetic`. If a new scan returns synthetic data, delete only that newly created scan via the owner-scoped API before exiting with an error. Never call the fixture adapter or fabricate a completed result.
- [ ] Do not make photo-only scans into consumption records. Dashboard intake comes from explicit manual consumption records created by this seed; users can confirm photo scans later in the app.
- [ ] Mark each item complete only after the API has returned and validated its resource ID. Print only a compact count/status summary.
